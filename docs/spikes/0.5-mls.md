# Spike 0.5 — MLS / `openmls`

**Question (ROADMAP):** is `openmls` workable for our group model and persistence needs?
**Question (ADR-002):** does the O(log n) group-scaling claim hold?
**Status:** ✅ **Passed on function.** ⚠️ **The ADR's stated justification was wrong; the
conclusion survives for a different and better reason.**
**Code:** `spikes/mls/` · `openmls 0.9.0`, ciphersuite `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`
**Date:** 2026-09-01

---

## Part 1 — functional exit criteria

All passed:

| Check | Result |
| :--- | :--- |
| Alice creates a group | OK |
| Bob joins via `Welcome` | OK |
| Application message Alice → Bob | OK |
| Application message Bob → Alice | OK |
| Charlie added; 3 members in sync | OK |
| All 3 members derive an identical exported secret | OK |
| Bob removed | OK |
| **Removed member cannot decrypt subsequent messages** | OK |
| Remaining member still decrypts correctly | OK |
| Group state reloaded from storage after simulated restart | OK |
| Reloaded group sends a message the peer decrypts | OK |

Two of these matter more than the rest:

**Post-compromise security is real and verified.** After removal, Bob processes his own removal
commit and then *fails* to decrypt the next message. This is asserted, not assumed — it is the
property the multi-device story in `ARCHITECTURE.md` §4.3 depends on.

**The exported secret is identical across all members.** This is what `ARCHITECTURE.md` §7 relies
on for media keying: voice and video keys derive from the MLS epoch secret, so calls inherit
forward secrecy and rekey automatically on membership change. Confirmed working.

Messages were routed through real TLS serialization and deserialization rather than passed as
in-memory structs, so these numbers are wire-realistic. Note that `into_protocol_message()` and
`into_welcome()` are `test-utils`-gated in openmls 0.9 — production code must use
`try_into_protocol_message()` and match on `MlsMessageBodyIn`.

## Part 2 — scaling

Measured at group sizes from 2 to 200, with and without the ratchet tree extension (results were
identical for commit size, so only one set is shown):

| Members | Commit bytes | Add member | App msg bytes | App msg encrypt |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 682 | 0.31 ms | **173** | **35.8 µs** |
| 4 | 883 | 0.68 ms | **173** | 39.2 µs |
| 8 | 1,246 | 2.47 ms | **173** | 50.9 µs |
| 16 | 1,938 | 1.70 ms | **173** | 38.1 µs |
| 32 | 3,285 | 1.53 ms | **173** | 39.4 µs |
| 64 | 5,944 | 2.47 ms | **173** | 65.4 µs |
| 128 | 11,228 | 3.75 ms | **173** | 47.7 µs |
| 200 | 17,171 | 7.27 ms | **173** | 52.0 µs |

### Finding 1 — application messages are O(1), and this is the real win

**173 bytes and ~45 µs at every group size from 2 to 200.** Perfectly flat. One encryption
produces one ciphertext that every member can decrypt.

This is the property that justifies MLS. A Signal-style pairwise design would need one
encryption and one ciphertext *per recipient*: at 200 members, 200× the CPU and 200× the
upstream bandwidth for every message sent. Since a chat client sends thousands of application
messages for every membership change, this is the operation that dominates.

### Finding 2 — commits are O(n), not O(log n)

Commit size grows **linearly at ~83 bytes per member** (predicted 11,178 bytes at 128 members,
measured 11,228). This is inherent to MLS, not a misconfiguration: a commit with a path update
encrypts the path secret to the resolution of each sibling subtree along the path, and those
subtree sizes sum to n−1. Disabling the ratchet tree extension changed nothing.

So **ADR-002's blanket claim of "O(log n) group operations" is incorrect.** The tree depth is
logarithmic; the broadcast commit is linear.

The decision still stands, and on firmer ground — the correct justification is Finding 1, not
the O(log n) framing.

### Finding 3 — commit fan-out is a real P2P bandwidth cost

At 200 members a commit is 17 KB, and in a P2P system with no delivery service the committer
broadcasts it to every member directly: **~3.4 MB of upstream for a single member joining.**
On a domestic upload link that is several seconds.

This sharpens open question #3 in `BRD.md` §10. It does not affect messaging, which is O(1), but
it does mean large-group *membership churn* needs thought — batching adds, or accepting that
200-member spaces have slow joins.

## Consequences

- **ADR-002 revised** — the decision is unchanged; its stated reasoning is corrected to
  "application messages are O(1)" rather than "group operations are O(log n)".
- **`ARCHITECTURE.md` §5.1 revised** for the same reason.
- `BRD.md` §10 open question #3 updated with the measured 17 KB / 3.4 MB fan-out figure.
- Production code must avoid the `test-utils`-gated conversion helpers.
- `openmls_sqlx_storage` exists and should be evaluated in Phase 1, since it would let MLS group
  state share the `nexus-store` SQLite pool rather than needing a parallel store.

## Not yet tested

- Concurrent commits from multiple members (the fork-resolution path). openmls ships
  `book_code_fork_resolution.rs` covering it; needs its own spike before Phase 1 completes.
- A client that misses commits for weeks — the recovery path. This is open question #5 in
  `THREAT-MODEL.md` §7 and remains unanswered.
- Welcome message size at scale, which is where the ratchet tree extension actually matters.
