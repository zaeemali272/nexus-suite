# Spike 0.3 — Voice pipeline

**Question (R1, ADR-005):** can `webrtc-audio-processing` + `opus` + `cpal` be wired together in
Rust with working echo cancellation?
**Status:** 🟡 **Substantially passed. The one thing that genuinely needs two machines — acoustic
echo cancellation in a real room — is still unverified.**
**Code:** `spikes/voice/` · `spikes/voice-shell.nix`
**Date:** 2026-09-01

---

## What was built

A complete working pipeline, not a mock:

```
mic ──cpal──> [AEC/NS/HPF] ──Opus 20ms──> QUIC datagram
                                              │
                                              ▼
speaker <──cpal── Opus decode <── jitter buffer + PLC
```

Four modes: `bench` (no hardware needed), `devices`, `recv <bind>`, `send <addr>`.

## 1. Dependencies build — ADR-005's core assumption holds

`webrtc-audio-processing` 2.1.0 compiles cleanly against the nixpkgs system library in **29
seconds**. This was the single biggest unknown in ADR-005: a C++ dependency that fails to build
would have forced writing DSP from scratch, which the ADR explicitly rejects as months of
specialist work.

`libopus`, `alsa-lib` and `webrtc-audio-processing` all resolve via pkg-config;
`spikes/voice-shell.nix` captures the environment.

## 2. Opus — comfortably real-time

48 kHz mono, 20 ms frames (960 samples), speech-like synthetic input:

| Target | Frame bytes | Actual | Encode | Decode |
| ---: | ---: | ---: | ---: | ---: |
| 16 kbps | 40 | 16.0 kbps | 142 µs | 16 µs |
| **24 kbps** | **60** | **24.1 kbps** | **55 µs** | **14 µs** |
| 32 kbps | 81 | 32.4 kbps | 59 µs | 16 µs |
| 48 kbps | 121 | 48.4 kbps | 68 µs | 20 µs |
| 64 kbps | 161 | 64.4 kbps | 72 µs | 23 µs |

Encoding a 20 ms frame costs ~55 µs — **0.3% of the real-time budget**. Packet loss concealment
works: decoding a dropped frame produces concealed audio, not silence, in 23.5 µs.

At 24 kbps, an 8-person mesh call costs 7 × 24 = **168 kbps upstream**, well inside the
`ARCHITECTURE.md` §7 estimate.

## 3. Echo cancellation — converges to 37 dB ERLE

Processing cost for AEC + NS + high-pass on a 10 ms frame: **p50 81 µs, p99 108 µs — 1.08% of
the real-time budget.**

ERLE (Echo Return Loss Enhancement) measured under far-end single talk, with a synthetic echo
path of 10 ms delay and 0.6 gain:

| Time | ERLE |
| ---: | ---: |
| 2 s | 35.7 dB |
| 4 s | **43.0 dB** |
| 10 s | 39.4 dB |
| 20 s | 37.2 dB |

**Converges within 2 seconds and holds around 37–43 dB.** For reference, 20 dB is generally
considered adequate and 30 dB+ good.

### A measurement error worth recording

The first version of this test reported **−4.4 dB** — apparently a total failure. It was not; the
methodology was wrong in two ways:

1. It measured during **double talk** (near and far end both active). ERLE is only meaningful
   under far-end single talk, because during double talk you cannot separate residual echo from
   near-end speech that noise suppression legitimately altered.
2. Near and far end were both generated by the same harmonic function, so they were highly
   correlated — AEC3 cannot distinguish echo from near-end speech when the two signals are nearly
   identical, and real speech is not like that.

Rewriting the test with a decorrelated broadband far-end reference and a silent near end moved
the result from −4.4 dB to +37 dB. **The AEC was working the whole time; the measurement was
broken.** Recorded here because the same trap will appear again during tuning.

Note also that the library's own `get_stats()` reports `echo_return_loss_enhancement: 0.18` —
which contradicts the measured 37 dB. Those stat fields appear unpopulated in this build; do not
rely on them.

## 4. End-to-end over QUIC — works, zero loss

Live loopback run, real microphone capture through the full pipeline:

```
played    897  lost 0  late 0  buffer 2 frames  underruns 64
sent      902 frames  14.8 kbps on the wire  rtt 141 µs  overruns 0
```

- **Zero lost frames, zero late frames, zero capture overruns** across ~900 frames (18 seconds).
- Jitter buffer holds steady at **2–3 frames (40–60 ms)** with no drift.
- 14.8 kbps actual against a 24 kbps target — Opus VBR correctly dropping the rate in a quiet
  room.
- 64 output underruns, all in a single blip at stream start, flat thereafter.
- No allocation in either audio callback.

## What is still unverified

**Mouth-to-ear latency has not been measured.** The exit criterion is < 150 ms, and the pipeline's
own contribution can be estimated (20 ms frame + 40–60 ms jitter buffer + device buffers), but the
real number needs a physical measurement — play a click, record it, measure the gap. Not done.

**Acoustic echo cancellation in a real room is unverified.** The 37 dB above is against a
synthetic echo path: linear, fixed delay, no reverb, no loudspeaker non-linearity, no clock drift
between the capture and playback devices. Real rooms have all four, and clock drift in particular
is what usually breaks AEC in practice. **This is what needs two machines.**

## How to run the two-machine test

On the receiving machine:

```bash
cd spikes
nix-shell voice-shell.nix --run "cargo run --release -p spike-voice recv 0.0.0.0:4433"
```

On the sending machine (same LAN; UDP 4433 must be reachable):

```bash
cd spikes
nix-shell voice-shell.nix --run "cargo run --release -p spike-voice send <receiver-ip>:4433 24"
```

**What to check:**

1. **Speakers on, not headphones, on both ends** — headphones defeat the entire point.
2. Talk on the sending machine. The receiving machine should play it back clearly.
3. Then run it in both directions at once and listen for echo. This is the real test.
4. Watch `lost` / `late` / `underruns` on the receiver and `overruns` on the sender. All should
   stay near zero on a healthy LAN.
5. Note the `buffer N frames` figure — that is the jitter buffer's live depth, and each frame is
   20 ms of added latency.

Currently the sender applies capture-side processing but the pipeline is **one-directional**, so
step 3 requires running `send` and `recv` on both machines simultaneously. Full duplex with a
shared AEC render reference is Phase 4 work.

⚠️ The QUIC transport in `spikes/voice/src/net.rs` **disables certificate verification** so two
machines can be paired with no setup. It is spike-only and must never be copied into the client
(ADR-003).
