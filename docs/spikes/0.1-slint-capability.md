# Spike 0.1 — Slint capability probe

**Question (R2, ADR-004):** can Slint handle rich text editing, cross-widget text selection, IME
input, and screen-reader output — the four capabilities a chat client needs and Slint was
suspected to be weakest at?
**Status:** ⚠️ **Three of four pass. Cross-message text selection does not exist and cannot be
worked around without custom implementation.**
**Method:** API inspection of Slint 1.17.1 sources (`builtins.slint`, `i-slint-core`,
`i-slint-common`, backend manifests). Presence and absence of API is definitive; runtime
behaviour of IME and screen readers is not, and is flagged below.
**Date:** 2026-09-01

---

## 1. Rich text — better than assumed, with specific gaps

ADR-004 assumed Slint was weak here. **It is stronger than expected.** Slint 1.17 ships a
`StyledText` element rendering a CommonMark subset:

| Supported | Not supported |
| :--- | :--- |
| Italics, strikethrough | Headings |
| **Inline** code | **Code blocks** |
| Links, with `link-clicked(link)` callback | **Images** |
| Ordered and unordered lists | Tables, block quotes |
| `<u>` underline | Sub/superscripts, horizontal rules |
| `<font color="...">` arbitrary text colour | Footnotes, math, other HTML |

Two gaps bear on P0 requirements:

- **FR-2.4 requires code blocks with syntax highlighting.** `StyledText` supports only *inline*
  code. However, `<font color="...">` accepts arbitrary colours, so **syntax highlighting is
  achievable by emitting coloured spans into the markup** — the highlighter runs in Rust and
  produces styled output. A code block becomes its own element with its own background, composed
  into the message rather than expressed as markdown.
- **Images cannot appear inside a `StyledText` run.** A message must therefore be rendered as a
  *sequence of blocks* — paragraph → `StyledText`, code block → custom element, image →
  `Image` — laid out vertically, not as one markdown string.

**Rich text *editing* is not supported.** `TextInput`/`TextEdit` are plain-text only; there is no
WYSIWYG composer. This is acceptable: Discord, Slack, and Element all use a markdown-source
composer, and matching them is fine.

## 2. Cross-widget text selection — **not supported, no workaround**

This is the real failure.

- `Text` and `StyledText` have **no selection capability at all** — no `selectable` property, no
  selection range, nothing. Their full property sets were inspected; selection is absent.
- Only `TextInput` supports selection (`selection-foreground-color`,
  `selection-background-color`, `cursor-position`, `anchor-position-byte-offset`, `select_all`),
  and strictly **within a single element**.

So "drag across three messages and copy the conversation" — table stakes in Discord, Slack, and
Element — is not achievable with stock Slint.

The partial workaround is a read-only `TextInput` per message, which gives selection *within one
message*. But `TextInput` is plain text, so this forfeits `StyledText` entirely:

> **Selectable or styled. Not both.**

That is a sharp constraint, and it lands directly on the message list — the single most important
surface in the product.

## 3. IME — supported

Real input-method support exists in core: `preedit_text` and `preedit_selection` on the key event
path (`input.rs`), preedit handling in `items/text_input.rs`, `preedit-text` exposed as a
`TextInput` property, and text layout via **parley** (`textlayout/sharedparley.rs`), a mature
shaping engine.

⚠️ Verified by API presence only. **Not tested by actually typing with a CJK or Indic IME** —
that requires manual interactive testing and should be done before Phase 3 UI work begins.

## 4. Accessibility — strong, and better than assumed

Slint uses **AccessKit** with platform backends for AT-SPI (Linux), macOS, Windows, and iOS
(`accesskit_unix`, `accesskit_macos`, `accesskit_windows`, `accesskit_ios`).

The role set is comprehensive and includes full ARIA landmark roles — `Banner`, `Complementary`,
`ContentInfo`, `Form`, `Main`, `Navigation`, `Region`, `Search` — plus `List`, `ListItem`,
`TextInput`, `Table`, `Tab`, and live-region support via `accessible-live-region`. Accessible
properties include `Label`, `Description`, `Value`, `ItemCount`, `ItemIndex`, `ItemSelected`,
`Expanded`, `ReadOnly`, and `PlaceholderText`.

Live regions matter specifically here: they are the mechanism by which a screen reader announces
an incoming message without the user navigating to it.

⚠️ Verified by API and dependency presence. **Not tested by driving an actual screen reader.**
Schedule an Orca test in Phase 5.

## Verdict on ADR-004

**Keep Slint.** Three of four capabilities pass, and combined with Spike 0.2's frame-time and
memory results, no alternative toolkit offers a better overall position — Tauri reintroduces the
browser engine the project exists to avoid, and Flutter costs 2–3× the memory and adds a second
language.

But the decision is now **conditional on two design commitments**, neither of which was in the
original plan:

1. **Message rendering is block-composed**, not a single markdown string: paragraphs via
   `StyledText`, code blocks as a custom element with `<font color>` syntax highlighting, images
   as `Image` elements.
2. **Cross-message selection must be custom-built**, or v1 ships with per-message selection only.
   This needs an explicit product decision — see below.

## Open decision for the user

Cross-message text selection is a genuine regression against every competitor. Three options:

| Option | Cost | Consequence |
| :--- | :--- | :--- |
| Accept per-message selection in v1 | Free | Users cannot copy a multi-message excerpt. Noticeable, survivable. |
| Build a custom selection layer | ~1–2 weeks in Phase 3 | Hit-testing text runs across list items and synthesising a selection overlay. Real work, no upstream support. |
| Add "copy message" affordances | ~2 days | Per-message copy button and a "copy last N" command. Mitigates without solving. |

**Recommendation:** ship the cheap affordances for v1, defer the custom selection layer to
post-v1, and revisit if user feedback shows it matters. Slint may also add selectable text
upstream — worth tracking.
