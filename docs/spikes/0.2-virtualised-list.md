# Spike 0.2 — Virtualised message list

**Question (R2):** can Slint scroll 100,000 variable-height messages at 120 fps?
**Status:** ✅ **Passed on frame time.** ⚠️ **The RSS budget in `BRD.md` §6.1 was measured against
the wrong metric and needs restating.**
**Code:** `spikes/ui/` · Slint 1.17.1, femtovg/OpenGL backend, Wayland
**Date:** 2026-09-01

---

## Method

A `ListView` bound to a `VecModel` of N messages with content-derived variable heights (26–100 px,
total viewport 5.45 M px at 100k). Continuous scroll driven at 4 ms intervals, sweeping deep into
the list so virtualisation is genuinely exercised rather than redrawing the first screen.

Frame cost is measured `BeforeRendering` → `AfterRendering` via `set_rendering_notifier` — the
actual work to produce a frame. Frame *interval* is also recorded, but it is vsync-capped by the
60 Hz display and only useful for spotting dropped frames.

## Frame time

| Messages | p50 | p90 | p99 | max |
| ---: | ---: | ---: | ---: | ---: |
| 500 | 1.93 ms | 2.79 ms | 3.34 ms | 6.99 ms |
| 2,000 | 2.24 ms | 2.85 ms | 3.72 ms | 4.71 ms |
| 20,000 | 2.37 ms | 2.90 ms | 3.63 ms | 4.43 ms |
| 100,000 | 1.97 ms | 2.83 ms | 4.12 ms | 5.71 ms |

**Render cost is flat from 500 to 100,000 messages.** Virtualisation works correctly — cost
tracks the visible window, not the model size. p99 of ~4 ms sits well inside the 8 ms target with
roughly 4× headroom.

**120 fps could not be confirmed**, because the test display is 60 Hz and frame interval is
vsync-capped at 16.7 ms. A 2 ms render cost implies ample headroom for 120 Hz, but this needs
re-running on a 120 Hz panel before the claim is made.

## Memory — and why the budget was wrong

Peak RSS at 100k messages was 101 MB, which breaches the 90 MB ceiling. Investigating that
produced the more useful finding:

| Backend | Messages | RSS | PSS | USS (private) |
| :--- | ---: | ---: | ---: | ---: |
| software | 2,000 | 22.3 MB | 15.8 MB | 15.1 MB |
| software | 100,000 | 39.8 MB | 33.4 MB | 32.7 MB |
| **femtovg (GPU)** | **2,000** | 83.3 MB | **39.0 MB** | 32.7 MB |
| femtovg (GPU) | 100,000 | 101.5 MB | **57.3 MB** | 51.1 MB |

Swapping the GPU renderer for the software one drops RSS from 83 MB to 22 MB at the same model
size. **~61 MB of the footprint is the Mesa/OpenGL driver stack, not Slint and not the
application.**

RSS counts shared library and driver pages at full weight in every process that maps them, which
overstates what the process actually costs the system. PSS — shared pages divided among their
sharers — is the honest measure:

- **Realistic working set (2,000 messages, GPU): PSS 39 MB, USS 33 MB.** Comfortably inside the
  60 MB target.
- Even the pathological 100k-resident case is PSS 57.3 MB, still under 60 MB.

A real client holds a window of messages plus caches, not the entire history in the model, so
2,000 is the representative figure and 100,000 is a stress bound.

## Consequences

- **`BRD.md` §6.1 restated in PSS**, with RSS recorded separately as an observability number.
  Measuring a GPU application's memory in RSS penalises it for driver pages it shares with every
  other GPU client on the system.
- The Electron comparison in `README.md` survives easily either way: ~83 MB RSS against
  Discord's 350–800 MB is still 4–9×.
- CI must measure PSS, not RSS, and must pin the backend — the two differ by 4×.
- Re-run on a 120 Hz display before claiming 120 fps anywhere.

## Caveats

Single machine, single GPU (Mesa, `/dev/dri/card1`), Wayland, 60 Hz. Driver memory varies
considerably across vendors — NVIDIA's proprietary stack in particular. Needs re-measurement on
Windows and macOS in Phase 5.
